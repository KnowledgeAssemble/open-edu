# The OpenEdu Way

> _"Learning is assembled, not delivered."_

---

# Purpose

The OpenEdu Way is the canonical body of knowledge for the OpenEdu project.

It captures the philosophy, design language, architecture, and engineering principles that guide every decision made within the project.

Its purpose is not to document everything.

Its purpose is to ensure that humans and AI agents make consistent decisions without requiring continuous interpretation.

---

# Vision

OpenEdu is building an open, modular, AI-native learning platform that enables anyone to create, share, and experience education.

Rather than treating learning as pages or videos, OpenEdu treats knowledge as interconnected modules that learners assemble into understanding.

Everything in OpenEdu—from architecture to interface design—should reinforce this philosophy.

---

# Core Principles

Every decision should align with these principles.

1. Philosophy before implementation.
2. Design language before user interfaces.
3. Accessibility by default.
4. Simplicity over novelty.
5. Composition over complexity.
6. Reuse before invention.
7. Open standards over vendor lock-in.
8. MVP before optimization.

When principles conflict, the higher principle wins.

---

# Canonical Hierarchy

The project follows a strict hierarchy of authority.

1. Volume I — Philosophy
2. Volume II — Design Language
3. Architecture Documentation
4. Figma Design System
5. Source Code

Higher layers define intent.

Lower layers implement intent.

Implementations should never redefine philosophy.

# Design Authority

OpenEdu owns its:

- philosophy
- design language
- design tokens
- interaction patterns

External design systems, UI libraries, and frameworks are implementation references.

They may adopt the OpenEdu language.

They do not define it.

---

# Decision Framework

Before introducing any feature, component, or design, verify:

- Is it consistent with Volume I?
- Is it consistent with Volume II?
- Does it improve learning?
- Does it reduce cognitive effort?
- Is it accessible?
- Is it reusable?
- Is it implementation-independent?
- Is it appropriate for the MVP?

If any answer is "no", reconsider the proposal.

---

# AI Collaboration

AI is an architectural collaborator.

Its responsibilities include:

- preserving philosophical consistency
- challenging unnecessary complexity
- identifying inconsistencies
- improving accessibility
- protecting MVP scope
- encouraging reuse
- proposing alternatives when appropriate

AI should not expand the roadmap without a genuine architectural reason.

---

# Long-Term Vision

The OpenEdu Way should become sufficiently clear that:

- contributors make consistent decisions,
- AI agents build compatible implementations,
- designers produce recognizable interfaces,
- learners experience one coherent ecosystem.

The goal is not documentation.

The goal is consistency.
